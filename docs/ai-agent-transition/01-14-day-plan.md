# 14 天核心执行计划

## 1. 使用方式

这份计划按每天 2 到 3 小时设计。每天都要有一个可以检查的产出，避免只看资料不写代码。

建议建立一个独立分支或目录，用于保存：

- 当天代码。
- 测试用例。
- Prompt（提示词）和模型配置。
- 评测数据。
- Trace（运行轨迹）或运行日志。
- 当天学习记录。

每天结束时回答三个问题：

1. 今天新增了什么可运行能力？
2. 今天发现了什么失败或不确定性？
3. 明天要把哪个问题变成测试或代码？

## 2. 14 天总览

| 天数 | 主题 | 当天产出 | 完成判断 |
|---|---|---|---|
| 第 1 天 | 最小 Agent（智能体）闭环 | 模型调用和结构化输出 | 能完成一次固定任务 |
| 第 2 天 | Prompt（提示词）与输出约束 | 诊断结果 Schema（结构约束） | 非法输出可被拒绝或修正 |
| 第 3 天 | 工具调用 | 3 个只读工具 | Agent 能正确选择工具 |
| 第 4 天 | 工具可靠性 | 异常、超时、重试、幂等测试 | 工具失败不会直接击穿流程 |
| 第 5 天 | Workflow（工作流）与状态 | 分类、检索、分析、输出流程 | 能查看当前阶段和中间结果 |
| 第 6 天 | 证据检索 / 简化 RAG（检索增强生成） | 本地日志和代码检索 | 输出结论能引用证据 |
| 第 7 天 | MCP（Model Context Protocol，模型上下文协议） | 一个 MCP Tool（工具）或 Server（服务端） | 能解释 MCP 的边界和用途 |
| 第 8 天 | Golden Dataset（黄金数据集） | 20 到 30 条评测样本 | 样本覆盖主要成功和失败场景 |
| 第 9 天 | 确定性测试 | Tool（工具）、Schema（结构约束）、状态和权限测试 | `pytest` 可自动执行 |
| 第 10 天 | 行为评测 | 任务完成度和证据评测 | 有可重复的评测报告 |
| 第 11 天 | Trace（运行轨迹）与可观测性 | 一次运行的完整轨迹 | 能定位失败发生在哪一步 |
| 第 12 天 | Agent（智能体）安全 | 注入、越权、敏感信息测试 | 高风险动作能被拦截 |
| 第 13 天 | 端到端演示 | CLI（命令行界面）或简单 API（应用程序接口）演示 | 从输入到缺陷草稿完整跑通 |
| 第 14 天 | 项目收尾和面试 | README、架构图、项目介绍 | 能用 90 秒讲清楚项目 |

## 3. 每天详细安排

### 第 1 天：跑通最小 Agent（智能体）

学习重点：

- 模型请求和响应的基本结构。
- System Prompt（系统提示词）、User Prompt（用户提示词）和上下文的职责。
- 结构化输出和普通文本输出的区别。
- 一次 Agent Run（智能体运行）的最小生命周期。

编码任务：

- 定义一个 `FailureInput`。
- 调用模型判断 CI 失败类型。
- 要求模型输出 JSON 或 Pydantic 对象。
- 暂时不接工具，先固定输入和固定输出。

建议的失败类型：

```text
CODE
TEST
ENVIRONMENT
DATA
UNKNOWN
```

当天产出：

- `classify_failure()`。
- 一个结构化结果模型。
- 至少 5 个手工样例。
- 一份记录：模型输出不稳定时表现在哪里。

完成判断：

- 输入同一条失败信息时，能稳定返回合法结构。
- 非法 JSON、缺少字段或未知分类能够被程序发现。

### 第 2 天：Prompt（提示词）和输出约束

学习重点：

- 如何把任务边界写进 Prompt（提示词）。
- 何时让模型输出枚举、列表、对象和置信度。
- 如何区分“模型判断”和“程序计算”。
- 为什么不能让模型直接决定危险操作。

编码任务：

- 定义 `DiagnosisResult`。
- 至少包含：
  - `category`
  - `summary`
  - `confidence`
  - `evidence_ids`
  - `next_action`
  - `needs_human_review`
- 对字段做枚举、长度和引用校验。
- 增加 3 个异常输出样例。

当天产出：

- 结构化输出 Schema（结构约束）。
- 输出校验函数。
- 失败输出的修正或重试策略。

完成判断：

- 业务规则不依赖模型“自觉遵守”。
- 程序能明确拒绝没有证据引用的结论。

### 第 3 天：设计 Tool（工具）并接入 Tool Calling（工具调用）

学习重点：

- Tool（工具）的职责边界。
- 参数 Schema（结构约束）和返回值 Schema（结构约束）。
- 只读工具与写入工具的区别。
- 工具描述如何影响模型选择。

最小工具集：

```text
search_log(query, run_id)
search_code(keyword, file_hint)
get_recent_changes(service, since)
```

编码任务：

- 为每个工具定义严格参数。
- 工具返回带 `evidence_id` 的结构化结果。
- 让 Agent（智能体）根据失败信息选择工具。
- 记录每次工具调用的名称、参数和结果状态。

当天产出：

- 3 个工具。
- 每个工具至少 3 个单测。
- 一次包含两步工具调用的运行记录。

完成判断：

- 工具输入非法时可以快速失败。
- 工具输出可以被 Agent（智能体）和评测程序共同消费。

### 第 4 天：工具可靠性和错误处理

学习重点：

- 超时、重试和降级。
- 可重试错误和不可重试错误。
- 幂等键和重复调用。
- 工具调用失败时如何让 Agent（智能体）继续或终止。

编码任务：

- 给工具增加超时。
- 为临时错误设置有限次数重试。
- 对危险或写入工具暂时不自动重试。
- 给每次调用增加 `call_id` 和 `idempotency_key`。
- 构造日志查询失败、代码查询为空、网络超时等样例。

当天产出：

- 工具错误分类表。
- 重试策略。
- 至少 5 个错误处理测试。

完成判断：

- 重试不会无限循环。
- 同一个写入动作不会因为重试产生重复结果。
- 工具失败后，最终输出能说明缺失了什么证据。

### 第 5 天：Workflow（工作流）和状态

学习重点：

- Agent Loop（智能体循环）与确定性 Workflow（工作流）的区别。
- 哪些步骤应该交给模型，哪些步骤应该由程序控制。
- Run（运行）、Turn（轮次）、Tool Call（工具调用）、Checkpoint（检查点）的关系。
- 为什么审批和恢复必须成为运行状态的一部分。

建议流程：

```text
intake
  -> classify
  -> collect_evidence
  -> diagnose
  -> draft_bug
  -> human_review
  -> finish
```

编码任务：

- 定义状态枚举。
- 保存每个阶段的开始、结束和错误。
- 允许从 `human_review` 恢复。
- 将工具调用结果和证据引用写入状态。

当天产出：

- 一份 State Schema（状态结构）。
- 一次可以暂停和恢复的本地运行。
- 一张 Workflow（工作流）图。

完成判断：

- 页面或进程重启后，至少可以通过持久化 JSON 恢复运行现场。
- 不需要从自然语言消息猜测当前阶段。

### 第 6 天：证据检索和简化 RAG（检索增强生成）

学习重点：

- 检索增强生成的基本流程。
- 关键词检索与向量检索的适用范围。
- 证据片段、来源和引用关系。
- “有相关内容”不等于“足以支持结论”。

编码任务：

- 准备本地 CI 日志、代码片段、历史缺陷数据。
- 先使用关键词、SQLite FTS 或简单文件索引。
- 每条检索结果包含：
  - `evidence_id`
  - `source_type`
  - `source_uri`
  - `content`
  - `score`
- 限制 Agent 只能引用检索返回的证据 ID。

当天产出：

- 一个本地检索工具。
- 至少 10 条带来源的证据数据。
- 5 个“证据不足”的测试样例。

完成判断：

- 最终诊断中的证据 ID 都能反查到真实内容。
- 检索不到时，Agent 会表达不确定，而不是编造来源。

### 第 7 天：MCP（Model Context Protocol，模型上下文协议）最小实践

学习重点：

- MCP 的基本概念：Tools（工具）、Resources（资源）、Prompts（提示模板）。
- MCP 与普通函数调用的关系。
- 工具发现、参数约束和权限边界。
- 为什么 MCP 不等于完整的 Agent 框架。

编码任务：

- 将 `search_log` 或 `search_code` 暴露为 MCP Tool。
- 给 Tool 写清晰的描述和输入 Schema。
- 增加最小权限限制，例如只允许访问样例数据目录。
- 记录一次 MCP 工具调用。

当天产出：

- 一个可运行的 MCP Server 或 MCP Tool。
- 一页 MCP 说明，回答“为什么这里使用 MCP”。
- 一个越权路径测试。

完成判断：

- 能解释 MCP 解决的是工具和上下文接入的标准化问题。
- 能说明真实系统中仍然需要认证、授权、审计和沙箱。

### 第 8 天：建立 Golden Dataset（黄金数据集）

学习重点：

- 为什么 Agent（智能体）不能只用几个手工 Demo（演示）验证。
- 正例、边界样例、对抗样例和不可回答样例。
- 期望结果应该尽量写成可检查的条件。

建议准备 20 到 30 条样本：

| 类型 | 数量建议 | 例子 |
|---|---:|---|
| 代码缺陷 | 5 | 断言失败、空指针、接口变更 |
| 测试缺陷 | 5 | 定位器失效、断言错误、用例过期 |
| 环境问题 | 4 | 依赖不可用、网络超时、容器异常 |
| 测试数据问题 | 4 | 数据不存在、状态污染、权限不足 |
| 证据不足 | 3 | 日志不完整、堆栈截断 |
| 安全对抗 | 3 | 日志注入、越权指令、伪造证据 |

当天产出：

- `cases.jsonl`。
- 每条样本的预期分类、必备证据类型和允许动作。
- 一份样本覆盖矩阵。

完成判断：

- 每条样本都能说清楚“什么算通过”。
- 评测标准不依赖一句模糊的“看起来不错”。

### 第 9 天：确定性测试

学习重点：

- Tool（工具）单测、Schema（结构约束）单测、Workflow（工作流）单测和权限单测。
- Mock（模拟）模型和 Mock（模拟）工具。
- 如何把不可控的模型行为替换成可控输入。

优先测试：

- 工具参数校验。
- 工具错误映射。
- 状态转移。
- 审批前禁止写入。
- 证据 ID 必须存在。
- 重试次数和幂等行为。
- 敏感字段脱敏。

当天产出：

- 一套 `pytest` 测试。
- 一张测试分层表。
- 至少 15 个确定性测试。

完成判断：

- 不依赖真实模型时，核心业务规则也能完整验证。
- 测试失败时能够定位到具体模块或状态。

### 第 10 天：Agent（智能体）行为评测

学习重点：

- 任务完成度和文本相似度的区别。
- LLM-as-Judge（大模型评审）的用途和局限。
- 规则评测、人工抽检和模型评审如何组合。
- 评测结果如何用于回归。

建议指标：

```text
任务通过率
工具选择准确率
工具参数正确率
证据引用准确率
根因分类准确率
危险动作拦截率
平均延迟
平均 Token / 成本
```

当天产出：

- 一个评测脚本。
- 一份基线结果。
- 至少 5 条失败样例的原因分析。

完成判断：

- 修改 Prompt（提示词）前后可以比较结果。
- 评测报告能说明“哪里变好了，哪里变差了”。

### 第 11 天：Trace（运行轨迹）和可观测性

学习重点：

- Run（运行）、Model Call（模型调用）、Tool Call（工具调用）、Guardrail（安全护栏）、Error（错误）的层级关系。
- 为什么最终答案无法替代完整 Trace。
- 失败回放需要保存哪些字段。

最小 Trace 字段：

- `run_id`
- `parent_id`
- `timestamp`
- `stage`
- `model`
- `prompt_version`
- `tool_name`
- `tool_args`
- `tool_result_status`
- `latency_ms`
- `token_usage`
- `error`

当天产出：

- 一次完整运行的 Trace（运行轨迹）JSON。
- 一个失败运行的回放记录。
- 一份失败定位说明。

完成判断：

- 能回答模型为什么调用某个工具。
- 能回答失败是在模型决策、工具执行、数据检索还是输出校验阶段发生的。

### 第 12 天：安全测试

重点测试：

- Prompt Injection（提示词注入）：日志内容试图改变 Agent 指令。
- Tool Injection（工具注入）：检索结果中包含恶意工具调用建议。
- 越权访问：工具参数访问不允许的目录、项目或用户数据。
- 敏感信息泄露：输出 Token、密码、手机号或内部地址。
- 未授权写入：没有人工审批就创建缺陷或重跑任务。
- 过度代理：模型提出超出任务范围的动作。

当天产出：

- 至少 10 条安全测试。
- 一份风险矩阵。
- 一套拒绝、脱敏或转人工策略。

完成判断：

- 高风险动作不是由模型单独决定。
- 失败响应不会暴露不必要的内部信息。

### 第 13 天：端到端演示

建议演示流程：

1. 输入一条失败的 CI 任务。
2. Agent（智能体）判断失败类型。
3. 调用日志和代码检索工具。
4. 汇总证据。
5. 输出根因分析。
6. 生成缺陷草稿。
7. 在审批前停止。
8. 人工确认后再模拟创建动作。

当天产出：

- 一个 CLI（命令行界面）、HTTP API（应用程序接口）或最小页面。
- 一段 3 到 5 分钟演示录屏，或完整终端运行记录。
- 一个正常流程和两个失败流程。

### 第 14 天：项目收尾和面试准备

需要完成：

- README（项目说明）。
- 架构图。
- 本地运行说明。
- 测试和评测命令。
- 评测结果表。
- 失败案例分析。
- 安全设计说明。
- 90 秒项目介绍。
- 2 到 3 条简历描述。

最终不要只展示“能回答问题”，而要展示：

- Agent（智能体）做了哪些决策。
- 工具做了哪些动作。
- 哪些动作被程序控制。
- 如何验证结果。
- 出错后如何定位和恢复。

## 4. 第三周可选增强

如果还有 7 天，不再横向学习多个框架，优先做下面内容：

### 第 15 天：接一个真实数据源

- 接真实 Git 仓库或脱敏代码目录。
- 接 CI 查询 API（应用程序接口）或读取真实流水线产物。
- 保留 Mock（模拟）模式，保证本地可重复运行。

### 第 16 天：增加模型和 Prompt（提示词）版本

- 为 Prompt（提示词）建立版本号。
- 保存模型名、参数和版本。
- 对同一批 Golden Case 做 A/B 评测。

### 第 17 天：补充成本和延迟

- 统计每个阶段的耗时。
- 统计模型调用次数和 Token。
- 对重复检索、重复工具调用做优化。

### 第 18 天：补可恢复运行

- 持久化状态和 checkpoint。
- 模拟进程重启。
- 验证从审批点或失败点恢复。

### 第 19 天：补工程质量

- 增加静态检查、类型检查和 CI。
- 为工具和评测数据加版本。
- 增加配置校验和运行参数说明。

### 第 20 天：整理求职材料

- 简历项目描述。
- 项目架构图。
- 评测报告。
- 常见问题答案。
- 项目演示脚本。

### 第 21 天：模拟面试

- 进行一次 30 分钟项目讲解。
- 自问自答 10 个 Agent（智能体）工程问题。
- 记录不能讲清楚的地方，回到代码补证据。

## 5. 忙碌时的最小版本

如果每天只有 1 小时，只保留下面路径：

```text
第 1 天：模型调用和结构化输出
第 2 天：两个只读工具
第 3 天：完整诊断流程
第 4 天：10 条 Golden Case（黄金测试样例）
第 5 天：确定性测试
第 6 天：安全和审批
第 7 天：README（项目说明）和面试表达
```

这时宁可少做功能，也要保留评测和测试。一个功能少但验证充分的 Agent（智能体）项目，比功能很多但只能现场演示一次的项目更适合面试。
