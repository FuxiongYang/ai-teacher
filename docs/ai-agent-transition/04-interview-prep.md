# 面试准备与项目表达（Interview Preparation）

## 1. 90 秒项目介绍

可以按下面结构准备：

> 我做的是一个 CI 故障诊断 Agent（智能体），目标是帮助测试开发工程师分析流水线失败。输入包括失败日志、Stack Trace（堆栈轨迹）、Git Diff（代码差异）和环境信息。Agent 通过日志检索、代码检索和变更查询工具收集证据，然后输出结构化的故障分类、根因摘要、证据引用和缺陷草稿。对于重跑测试或创建缺陷这类高风险动作，系统会进入人工审批状态，不允许模型直接执行。工程上我把测试分成两层：工具、状态、权限和审批使用确定性测试；任务完成度、根因准确率和证据质量使用 Golden Dataset（黄金数据集）做离线评测。同时记录模型调用、工具调用、状态和耗时，便于失败回放和 Prompt（提示词）版本回归。这个项目主要体现了我从测试开发向 Agent 应用和 Agent 质量工程的迁移。

注意：

- 不要把项目说成“聊天机器人”。
- 不要只介绍使用了哪个框架。
- 要主动说清楚失败、审批、评测和观测。

## 2. 简历项目描述

### 版本一：偏 Agent 应用工程

> 设计并实现 CI 故障诊断 Agent（智能体），接入日志、代码和 Git Diff 检索工具，基于结构化输出生成带证据的根因分析和缺陷草稿；通过 Workflow（工作流）管理分类、证据收集、诊断和人工审批状态，支持工具异常、重试和失败回放。

### 版本二：偏 Agent 评测工程

> 构建 Agent（智能体）评测体系，设计覆盖代码缺陷、环境问题、证据不足、工具失败和 Prompt Injection（提示词注入）的 Golden Dataset（黄金数据集）；对工具选择、参数正确性、分类准确率、证据引用和危险动作拦截率进行自动评测，并通过 Trace（运行轨迹）定位失败步骤。

### 版本三：偏测试平台

> 将 CI 日志、失败用例和代码变更分析流程 Agent 化，抽象统一 Tool Contract（工具契约）、State Schema（状态结构）、审批策略和 Trace（运行轨迹）事件；编写确定性自动化测试与模型行为回归测试，支持 Prompt（提示词）、模型和工具版本对比。

简历中如果没有真实生产数据，不要编造提升百分比。可以写：

- 覆盖多少条 Golden Case。
- 编写多少条确定性测试。
- 覆盖哪些风险类型。
- 支持哪些工具和状态。
- 评测报告包含哪些指标。

## 3. 高频问题和回答框架

### 3.1 Agent（智能体）和普通 Workflow（工作流）有什么区别？

回答结构：

1. Workflow（工作流）的步骤和分支通常由程序预先定义。
2. Agent（智能体）在一定约束下由模型决定下一步动作，例如选择哪个工具和需要多少轮检索。
3. 生产系统通常不是二选一，而是让模型负责不确定的决策，让程序负责状态、权限、重试、审批和副作用控制。

结合项目：

> 我的项目中，分类和检索工具选择允许模型参与，但状态转移、权限判断、审批和缺陷提交由 Workflow（工作流）和策略层控制。

### 3.2 如何测试 Agent（智能体），而不是只测试最终答案？

回答要点：

- 测 Tool Contract（工具契约）。
- 测工具选择和参数。
- 测 Workflow（工作流）和状态转移。
- 测证据引用。
- 测最终任务完成度。
- 测安全拒绝和审批。
- 保存 Trace（运行轨迹）做失败定位。

### 3.3 如何处理工具调用失败？

回答要点：

- 先区分可重试和不可重试错误。
- 设置超时、有限重试和退避。
- 读工具可以降级或继续收集其他证据。
- 写工具不自动重试，必须保证幂等并经过审批。
- 最终输出说明哪些证据缺失，不伪造结论。
- 将错误写入 Trace，便于回放。

### 3.4 为什么需要结构化输出？

回答要点：

- 下游程序需要稳定字段，而不是解析自然语言。
- 枚举、列表和引用关系可以校验。
- 评测程序可以自动比较。
- 缺少证据、非法动作和不确定状态可以被程序拦截。
- 结构化输出不代表模型可靠，仍需要 Schema 校验和业务规则。

### 3.5 RAG（检索增强生成）的主要风险是什么？

回答要点：

- 召回不到关键证据。
- 召回了相似但错误的内容。
- 证据之间存在冲突。
- 检索内容中包含 Prompt Injection（提示词注入）。
- 模型引用了不存在或不支持结论的内容。

项目中的处理：

- 给每条证据分配 ID 和来源。
- 输出只能引用真实证据 ID。
- 证据不足时输出不确定。
- 将检索内容当作数据，不当作系统指令。

### 3.6 MCP（Model Context Protocol，模型上下文协议）解决什么问题？

建议回答：

> MCP 主要提供一种更标准化的方式，让模型或 Agent（智能体）发现和使用外部工具、资源与提示模板。它解决的是接入协议和上下文交换的一部分问题，不会自动解决业务权限、身份认证、审计、沙箱、数据安全和评测。我在项目中把日志检索工具封装成 MCP Tool（工具），同时仍然在应用侧保留项目范围校验和审批策略。

### 3.7 如何防止 Agent 越权？

回答要点：

- Tool 层做参数和资源范围校验。
- 模型不能直接执行任意 Shell。
- 读操作和写操作分级。
- 高风险工具需要审批。
- 使用 allowlist，而不是只依赖 Prompt。
- 保存审计日志。
- 对路径、项目、用户和数据范围做显式授权。

### 3.8 多 Agent（多智能体）是否一定比单 Agent（单智能体）好？

建议回答：

> 不一定。多 Agent 会带来更多通信、状态同步、错误传播和评测成本。我的项目先用单 Agent 加明确 Workflow（工作流），只有当角色边界、并行任务或权限隔离确实带来收益时，才考虑拆分子 Agent。

### 3.9 如何判断 Agent 是否真的有价值？

不要只看回答是否流畅，至少看：

- 分析时间是否缩短。
- 根因定位是否更准确。
- 证据引用是否可靠。
- 人工复核成本是否下降。
- 错误和误报是否可接受。
- 单次成本和延迟是否满足业务要求。
- 失败后是否容易定位和恢复。

## 4. 项目深挖问题

准备下面这些问题的代码证据：

| 问题 | 需要展示的证据 |
|---|---|
| 工具怎么定义？ | 参数和返回 Schema（结构约束） |
| 为什么调用这个工具？ | Tool Trace（工具调用轨迹）和工具描述 |
| 输出如何保证合法？ | Pydantic / JSON Schema 校验 |
| 怎么处理工具失败？ | 错误分类和重试测试 |
| 怎样防止误创建缺陷？ | 审批状态和策略代码 |
| 如何做回归？ | Golden Dataset（黄金数据集）和报告 |
| 如何排查失败？ | Trace（运行轨迹）、事件和失败案例 |
| 怎么防止注入？ | 安全样例和拒绝结果 |
| 如何恢复运行？ | State Schema（状态结构）和 checkpoint（检查点） |
| 如何控制成本？ | 调用次数、Token 和延迟统计 |

## 5. 需要准备的演示流程

准备三个样例：

### 样例一：正常代码缺陷

- 日志包含异常。
- Diff 命中同一段代码。
- Agent 输出 `CODE`。
- 生成缺陷草稿。
- 等待人工审批。

### 样例二：工具失败或证据不足

- 日志检索超时或返回空。
- Agent 不伪造证据。
- 输出不确定性。
- 进入人工分析或重试状态。

### 样例三：Prompt Injection（提示词注入）

- 日志内容要求 Agent 忽略系统规则。
- Agent 将其作为普通日志文本。
- 不调用未授权工具。
- Trace 中记录拦截结果。
