# 测试开发工程师转 AI Agent（智能体）学习路线

这组文档记录一条面向测试开发工程师的短周期转型路线。目标不是在两三周内成为大模型算法工程师，而是完成一个可运行、可评测、能解释、能展示的 Agent（智能体）项目，并把已有的测试开发经验迁移到 Agent 质量工程和 Agent 应用工程中。

本文档组采用“中文主述、英文（English）保留”的方式：自然语言说明优先使用中文；技术术语、官方产品名、代码标识、字段名、枚举值、命令和链接保留 English，必要时在首次出现处补充中文释义。

## 1. 目标定位

优先考虑下面三类岗位：

1. AI Agent（智能体）应用工程师
2. AI 应用测试 / Agent（智能体）评测工程师
3. AI 测试平台或智能化质量工程师

推荐的转型路径是：

```text
测试开发工程师
    -> AI 应用测试 / Agent（智能体）评测
    -> Agent（智能体）应用工程
```

你的既有优势：

- 熟悉测试设计、边界分析和异常分类。
- 有自动化测试和工程开发经验。
- 理解 CI、日志、缺陷、回归和质量门禁。
- 能从用户场景出发设计可验证的行为。

需要新增的核心能力：

- 调用大模型并约束结构化输出。
- 设计可靠的 Tool Schema（工具参数结构）和工具执行边界。
- 组织 Agent Workflow（工作流）、状态和恢复。
- 设计 Agent 评测集和回归测试。
- 处理 Prompt Injection（提示词注入）、越权和敏感信息问题。
- 使用 Trace（运行轨迹）定位 Agent 的失败步骤。

## 2. 学习目标

两周核心目标：

- 能独立写出一个单 Agent（智能体）+ 多工具的应用。
- 能解释 Agent（智能体）、Workflow（工作流）、Tool Calling（工具调用）、RAG（检索增强生成）、MCP（Model Context Protocol，模型上下文协议）的基本关系。
- 能为 Agent 编写确定性单测和行为评测。
- 能记录一次完整运行的模型、工具、状态和错误信息。
- 能识别常见安全风险，并加入最小防护。
- 能用一个完整项目回答面试中的工程问题。

第三周增强目标：

- 接入一个真实或半真实的外部系统。
- 增加模型或 Prompt（提示词）版本回归。
- 补充成本、延迟、失败率和可恢复运行。
- 完善 README、架构图、评测报告和简历表述。

## 4. 中英术语速查

| 中文 | English | 本路线中的含义 |
|---|---|---|
| 智能体 | Agent | 能根据任务和上下文选择行动的模型驱动程序 |
| 工作流 | Workflow | 由程序控制的阶段、分支和状态转移 |
| 工具 | Tool | Agent 可以调用的外部能力 |
| 工具调用 | Tool Calling | 模型请求程序执行某个 Tool 的过程 |
| 状态 | State | 系统需要保存和恢复的运行事实 |
| 运行轨迹 | Trace | 一次运行中模型、工具、状态和错误的记录 |
| 结构约束 | Schema | 输入或输出必须满足的字段和类型定义 |
| 检索增强生成 | RAG | 先检索外部证据，再让模型生成结果 |
| 黄金数据集 | Golden Dataset | 用于稳定回归的人工准备样本集 |
| 大模型评审 | LLM-as-Judge | 使用模型辅助评估 Agent 输出质量 |
| 提示词注入 | Prompt Injection | 输入内容试图改变模型原有指令的攻击 |
| 模型上下文协议 | MCP（Model Context Protocol） | 连接模型、工具、资源和提示模板的标准协议 |
| 人工审批 | Approval | 高风险动作执行前的人工确认步骤 |
| 检查点 | Checkpoint | 支持暂停、恢复和失败重放的运行保存点 |

## 5. 核心项目

建议围绕一个项目学习所有知识点：

> CI 故障诊断与缺陷草稿 Agent（智能体）

输入 CI 日志、失败用例、Stack Trace（堆栈轨迹）和 Git Diff（代码差异），Agent（智能体）通过工具检索代码和日志，判断失败类型，给出带证据的根因分析，并生成缺陷草稿。真正创建缺陷或重跑测试前，需要经过人工确认。

这个项目适合你的原因：

- 业务场景和测试开发经验直接相关。
- 工具调用、RAG（检索增强生成）、状态、审批、评测和安全都能自然出现。
- 可以先用本地 Mock（模拟）数据完成，再逐步接入真实系统。
- 结果容易用准确率、证据命中率、工具调用正确率和安全拒绝率衡量。

## 6. 学习原则

### 6.1 先跑通闭环，再补局部深度

第一版只需要包含：

```text
输入任务
    -> Agent（智能体）判断
    -> 调用工具
    -> 汇总证据
    -> 输出结构化诊断
    -> 生成缺陷草稿
```

不要在第一周就投入大量时间搭建复杂前端、向量数据库、Multi-Agent（多智能体）或真实生产环境。

### 6.2 把模型行为拆成可验证的步骤

最终文本不是唯一测试对象。至少要检查：

- 是否选择了正确的工具。
- 是否传入了正确的参数。
- 是否使用了允许的数据范围。
- 是否引用了足够的证据。
- 是否正确处理工具失败。
- 是否在高风险动作前停下来等待审批。
- 是否能够在模型版本或 Prompt 变化后发现回归。

### 6.3 让工程基础服务于项目

Python、异步、数据库、Docker 和 CI 只在项目遇到问题时查漏补缺。当前阶段不安排单独的基础课程，避免学习路线再次膨胀。

### 6.4 保留主线，增加一个替代框架视角

OpenAI Agents SDK 继续作为默认主线，保证两周内可以完成项目闭环。为了补充 Agent 工程视野，不需要把所有框架都学一遍，只选择一个与目标岗位最相关的替代框架做局部实践：

- `LangGraph`：优先用于第 5 天的 `Workflow`、`State`、`Checkpoint` 和人工审批。
- `LlamaIndex`：优先用于第 6 天的 RAG、文档数据和证据检索。
- `PydanticAI`：优先用于第 1～2 天的结构化输出，或第 9 天的类型安全测试。
- `Google ADK`：只有在目标岗位明确使用 `Gemini`、`Vertex AI` 或 `Google Cloud` 时才纳入核心实践。

不要同时重写四套项目。统一输入、Tool Schema、State、Evidence 和 Golden Case，只替换一个局部实现，才能看出框架差异并控制学习成本。具体对比见：[Agent 工程框架对比与选择](./07-framework-comparison.md)。

### 6.5 Go 生态放在主线之后梳理

如果后续想做 Go 方向的 Agent 工程，可以在 14 天主线之后增加一周：[Go AI Agent 生态补充周](./08-go-agent-ecosystem-week.md)。这一周不重写完整项目，只做：

- `Eino` 最小 Agent / Workflow Demo。
- `OpenAI Go SDK` 底层模型调用理解。
- `MCP Go SDK` 工具协议理解。
- `Google ADK for Go`、`tRPC-Agent-Go`、`LangChainGo`、`Genkit Go`、`Microsoft Agent Framework for Go` 的选型对比。
- 一份面试可用的 Go 生态判断材料。

## 7. 完成标准

完成这组路线后，至少应有以下交付物：

- 一个可以本地运行的 Agent（智能体）项目。
- 3 到 5 个具备清晰 Schema（结构约束）的工具。
- 20 到 30 条 Golden Case（黄金测试样例）。
- 确定性单测和 Agent 行为评测。
- 一份评测结果表和失败案例分析。
- 一次完整运行的 Trace（运行轨迹）或日志。
- 一组安全测试用例。
- 一份架构图和 README。
- 一段 90 秒项目介绍。
- 两到三条可以放入简历的项目描述。

## 8. 时间分配建议

每天如果有 2 到 3 小时，可以按下面比例分配：

| 内容 | 比例 | 说明 |
|---|---:|---|
| 编码实现 | 50% | 每天必须有可运行的代码产出 |
| 阅读和概念 | 20% | 只读当前任务需要的资料 |
| 测试与评测 | 20% | 从第一周开始同步建设 |
| 复盘与表达 | 10% | 记录问题、结论和面试说法 |

如果当天时间不足，优先级顺序是：

```text
跑通主流程
    -> 补确定性测试
    -> 补行为评测
    -> 补安全和可观测性
    -> 补工程细节
```
